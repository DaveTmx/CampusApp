## Lecturer sign-in is now protected
- **Demo lecturer removed from release builds.** The demo accounts (including `lecturer123`) are created only when `BuildConfig.DEBUG` is true.
- **Staff setup is a separate, verified step** (`auth/StaffSetupActivity`). An email can set up a lecturer account only if it is on the approved staff list (`util/StaffAccess`). The account is created only after a code emailed to that address has been confirmed, so the person must be able to read that mailbox.
- **The release staff list is empty.** IT must supply the approved addresses in `StaffAccess.APPROVED_STAFF_EMAILS`. Until then, nobody can set up a lecturer account in a release build.
- **Every staff sign-in needs password plus emailed code.** After the right password, the app emails a 6-digit code (`util/OtpPrompt`). No session starts until the code is confirmed (`AuthViewModel.finishStaffSignIn`).
- **Lockout:** five wrong passwords lock the account for 15 minutes (`LocalAuthRepository`).
- **Stronger hashing:** PBKDF2-HMAC-SHA256, 120,000 iterations, 256-bit key, random salt. Old single-pass SHA-256 hashes still work and are upgraded on the next successful sign-in.

## Student verification
- Registration already emails a code, and the account is created only after the code is confirmed. An account that has not been verified cannot exist, so it cannot sign in.

## OTP hardening
- In release builds, codes are never shown on screen. If EmailJS is not configured, sending fails with "Email codes are not set up yet".
- Debug builds keep the on-screen code so the flow can be tried without email.

## Limits to be aware of
- Sign-in and staff checks run on the phone only. A rooted phone, or someone with the APK and a rooted device, can read the stored accounts. Real protection needs the server (`backend/`) to check passwords and codes. Moving staff sign-in there is the next step.
- The code check happens in the app. Once the server exists, the server should issue the session only after the code is verified.
- The approved staff list must be supplied by the university. The code does not know the university's domain.
- PBKDF2 takes roughly 100 to 400 ms per sign-in on a phone, so it runs on the same thread as the sign-in screen.
